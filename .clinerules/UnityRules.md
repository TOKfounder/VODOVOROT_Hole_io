# Cline Rules for Unity Project

## File editing restrictions
- NEVER modify files in `Library/`, `Temp/`, `Logs/` — these are generated by Unity.
- NEVER change `.meta` files manually unless explicitly asked (they link GUIDs).
- Prefer editing `.cs` scripts in `Assets/Scripts/`.

## Code style for C# scripts
- Use PascalCase for public methods and properties.
- Use camelCase for private fields (prefixed with `_` optional).
- Add [SerializeField] for private fields that need inspector visibility.
- Always wrap Debug.Log in #if UNITY_EDITOR for performance.

## Unity‑specific best practices
- Use `GetComponent<T>()` sparingly; cache references in Awake() or Start().
- Avoid `FindObjectOfType<T>()` in Update() methods.
- For object pooling, use `UnityEngine.Pool` namespace.

## Allowed terminal commands
- `git status`, `git diff` — always allowed.
- `dotnet build` — allowed only in `Assets/` directory.
- `rm` and `rmdir` — ask for approval every time.

## Version control
- Before any refactoring, run `git checkout -- .` to discard unwanted changes.
- Commit messages must follow format: `type(scope): description` (e.g., `feat(player): add double jump`).
